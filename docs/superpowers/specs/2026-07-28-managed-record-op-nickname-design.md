# 数据管理批量识别 OP 昵称设计

## 目标

在现有“数据管理”批量导入流程中，对包含 OP 的导入记录调用腾讯 QQ
用户信息接口，取得返回的 `nickname` 并保存。数据管理列表在 OP 字段后新增
“OP昵称”列。

昵称识别失败不能阻止记录导入。所有昵称查询固定使用抖音 AppID
`1105602870`。

## 当前链路

批量导入的真实链路为：

```text
public/admin/records.js
  -> POST /api/admin/records/import-text
  -> routes/admin-records.js
  -> lib/managed-records.js#importManagedRecordText
  -> managed_records
```

数据管理当前支持三种导入格式：

1. 谷歌号：`谷歌号----谷歌密码----谷歌辅助`
2. OP：单行五段 OP 全参
3. 综合：`谷歌号----密码----辅助----OP全参`

现有 `managed_records` 没有 AppID 和 OP 昵称字段。此功能不增加每条记录的
AppID 选择，统一使用已确认的抖音 AppID。

## 方案选择

采用服务端导入时同步识别。

未采用浏览器直连腾讯接口，因为它会把完整 OP Token 暴露给浏览器环境，
并存在跨域及浏览器日志泄露风险。未采用后台异步任务，因为当前功能不需要
额外任务队列、轮询状态和延迟展示。

## 数据模型

为 `managed_records` 新增：

```sql
op_nickname text not null default ''
```

旧记录在迁移后自动得到空昵称，不需要回填。DTO 新增 `opNickname`。

OP 昵称是可变化的展示资料，不能作为唯一标识、关联键或导入去重依据。

## 昵称查询组件

新增独立的服务端昵称查询模块，职责如下：

1. 使用现有 `parseOpToken()` 解析 OP，避免把 `openid` 和
   `access_token` 写反。
2. 固定使用 AppID `1105602870`。
3. 请求：

   ```text
   GET https://graph.qq.com/user/get_simple_userinfo
   ```

4. 查询参数：
   - `access_token`：OP 第 2 段
   - `oauth_consumer_key`：`1105602870`
   - `openid`：OP 第 1 段
5. 单次请求超时约 5 秒。
6. 仅当返回 `ret === 0` 且 `nickname` 为非空字符串时返回昵称。
7. 腾讯错误、超时、网络失败、响应格式错误和无昵称统一返回未识别结果，
   不向上抛出导致批量导入失败的异常。

模块支持依赖注入，使自动化测试能够使用本地假查询器，测试过程中不发送
真实 OP 到腾讯。

## 批量导入数据流

批量导入按以下顺序执行：

1. 解析并校验全部导入行。
2. 收集 OP 和综合记录中的 OP。
3. 按完整 OP 值去重，同一批相同 OP 只查询一次。
4. 在数据库事务开始前，以最多 5 个并发查询昵称。
5. 将查询结果合并回各条导入数据。
6. 开启数据库事务，执行现有去重、互补绑定、新增和更新逻辑。
7. 提交事务并返回导入统计。

昵称查询不能在数据库事务内部等待，避免外部腾讯接口延迟长期占用事务和
数据库连接锁。

谷歌号三段导入不触发昵称查询。

## 合并规则

昵称字段遵循以下规则：

- 新记录识别成功：保存新昵称。
- 新记录识别失败：保存空字符串并继续导入。
- 已存在相同 OP 且昵称为空，重新导入识别成功：补写新昵称。
- 已存在相同 OP 且已有昵称，本次识别成功：更新为腾讯最新昵称。
- 已存在相同 OP 且已有昵称，本次识别失败：保留旧昵称，不能用空值覆盖。
- 清除单条 OP：同时清空 OP 昵称。
- 批量清除 OP：同时清空所有选中记录的 OP 昵称。

OP 昵称不参与谷歌号或 OP 唯一性判断。

## API 返回

记录 DTO 增加：

```json
{
  "opNickname": "腾讯返回的昵称"
}
```

批量导入结果在现有字段基础上增加：

```json
{
  "nicknameDetectedCount": 1,
  "nicknameFailedCount": 2
}
```

统计按本次参与昵称识别的唯一 OP 计算：

- `nicknameDetectedCount`：成功取得非空昵称的唯一 OP 数量。
- `nicknameFailedCount`：未取得昵称的唯一 OP 数量。

接口响应及服务端日志不得包含腾讯请求 URL、完整 OP、`access_token`、
`pay_token` 或 `pfkey`。

## 管理页面

数据管理表格在“OP”后增加“OP昵称”列，并为列宽增加对应样式。

昵称为空时显示空白，不显示错误文案。批量导入完成提示显示：

```text
已导入 N 条记录，识别昵称 X 条，未识别 Y 条
```

如果存在跳过的重复记录，继续保留现有“跳过重复 N 条”提示。

当前功能不增加昵称筛选框，也不在手工新增/编辑表单中提供昵称编辑字段。

## CSV 导出

CSV 在“OP”后增加“OP昵称”列。导出的昵称按普通 CSV 文本进行转义，不导出
昵称识别状态或腾讯错误信息。

## 错误处理

以下情况均视为昵称未识别，但不影响导入：

- 腾讯返回非零 `ret`
- `nickname` 缺失或为空
- OpenID 无效
- Access Token 无效或过期
- AppID 或应用权限不匹配
- 请求超时
- DNS、TLS 或其他网络错误
- 响应不是预期 JSON

导入格式、数据库写入和现有业务校验错误仍按原有行为使请求失败并回滚。

## 安全

- 昵称查询只在服务端发起。
- 不记录完整请求 URL或任何完整 Token。
- 异常信息只保留可公开的错误类型，不拼接 OP 内容。
- 自动化测试只使用伪造 OP 和注入查询器。
- 数据库只新增昵称，不额外保存腾讯原始响应。

## 测试

采用测试驱动实现，至少覆盖：

1. 数据库迁移新增 `op_nickname`，旧记录默认空字符串。
2. DTO 和列表接口返回 `opNickname`。
3. OP 导入识别成功并保存昵称。
4. 综合导入识别成功并保存昵称。
5. 腾讯返回失败时记录仍成功导入且昵称为空。
6. 网络异常或超时时记录仍成功导入。
7. 同批重复 OP 只调用一次昵称查询器。
8. 已有空昵称能在重复导入时补写。
9. 本次识别失败不覆盖已有昵称。
10. 单条和批量清除 OP 时同步清空昵称。
11. 管理页面显示“OP昵称”表头和对应单元格。
12. CSV 在 OP 后导出“OP昵称”列。
13. 批量导入响应及页面提示包含成功、失败识别数量。
14. 测试输出和错误响应不泄露完整 Token。

## 验收标准

- 批量导入包含 OP 的记录后，腾讯返回的昵称立即显示在“OP昵称”列。
- 昵称接口失败不会减少正常导入数量。
- 固定使用抖音 AppID `1105602870`。
- 重复 OP 查询在同一批内去重。
- 清除 OP 不留下旧昵称。
- CSV 与列表字段保持一致。
- 现有数据管理、短 OP、公开上号和用户中心测试无回归。
