# 历史 OP 昵称批量补全设计

## 目标

在后台“数据管理”增加“批量补全OP昵称”按钮，为当前登录账号名下已有 OP、但 `op_nickname` 为空的历史记录补全昵称。

## 范围

- 仅处理 `owner_id` 等于当前登录管理员 ID 的记录。
- 仅处理 `op_value` 非空且 `op_nickname` 为空的记录。
- 不处理其他管理员的记录。
- 不覆盖已有昵称。
- 不增加后台任务队列或任务状态表。

## 后端接口

新增：

```text
POST /api/admin/records/backfill-op-nicknames
```

接口必须经过现有管理员登录校验。服务层先查询符合条件的记录，对相同完整 OP 去重，然后复用现有 `lookupOpNicknames`：

- 固定 AppID：`1105602870`
- 最大并发数：5
- 单次请求超时：5000 毫秒
- 单个查询失败返回空昵称，不中断整批处理

腾讯查询完成后，只更新成功识别的记录。更新 SQL 必须再次约束 `owner_id`、`op_value` 和空昵称，避免覆盖查询期间被其他请求写入的新昵称。

接口返回：

```json
{
  "pendingCount": 10,
  "updatedCount": 7,
  "failedCount": 3
}
```

- `pendingCount`：本次扫描到的待补全记录数量。
- `updatedCount`：实际成功写入昵称的记录数量。
- `failedCount`：未识别数量，等于 `pendingCount - updatedCount`。

没有待补全记录时返回三个零，不发起腾讯请求。

## 前端交互

在数据管理顶部操作栏增加“批量补全OP昵称”按钮。

点击后：

1. 显示确认提示，说明只处理当前账号名下昵称为空的历史 OP。
2. 确认后禁用按钮，文案改为“正在补全…”。
3. 请求补全接口。
4. 成功后刷新当前表格。
5. 根据结果显示：
   - 无待补全项：`没有需要补全的OP昵称`
   - 有待补全项：`待补全 N 条，成功 X 条，未识别 Y 条`
6. 无论成功或失败都恢复按钮状态；接口错误沿用现有后台错误提示机制。

## 数据一致性与安全

- 查询昵称发生在数据库写入之前，不在数据库事务中等待腾讯网络。
- 相同 OP 在一次补全中只请求一次，但其成功昵称可更新多条对应记录。
- 仅使用参数化 SQL。
- 不记录或返回完整 OP、access token、pay token、pfkey 或腾讯请求 URL。
- 昵称失败不会清空或改变任何记录。
- 测试使用注入的离线查询函数，不向腾讯发送真实凭据。

## 测试

后端测试覆盖：

- 当前账号的空昵称记录被补全。
- 其他账号记录不被处理。
- 已有昵称不被覆盖。
- 相同 OP 只查询一次，并可更新多条符合条件的记录。
- 部分或全部查询失败时其他成功记录仍写入。
- 无待补全记录时不调用昵称查询。
- 返回统计值准确。

前端测试覆盖：

- 页面包含补全按钮。
- 点击流程包含确认、禁用、请求、刷新与恢复。
- 空结果和普通结果提示文案正确。
